# 01 · 系统架构

---

## 1. 架构原则（先立规矩，再写代码）

| # | 原则 | 具体约束 |
|---|---|---|
| P1 | **单一可信源** | PostgreSQL 是唯一事实来源；Redis 只做队列/缓存，丢数据不影响正确性 |
| P2 | **计算与接口分离** | API 进程只读数据库；任何重计算在 Worker 进程；接口 P99 < 300ms |
| P3 | **时间可回溯** | 所有业务表带 `asof` 或 `created_at`；任何结论能回答"当时用的是什么数据" |
| P4 | **失败隔离** | 一个采集器/一个品种失败，不阻断其它；失败入 `fetch_log` 并可重放 |
| P5 | **可解释优先于精度** | 宁可 55% 命中率但每条可拆解，不要 60% 但黑箱 |
| P6 | **配置外置** | 密钥、连接串只走环境变量；`.env` 永不入库 |
| P7 | **契约先行** | 前后端以 OpenAPI 为准，前端类型由 schema 生成，不手写两遍 |

## 2. 分层架构

```
┌──────────────────────────────────────────────────────────────────────────┐
│ L4 产品层  apps/web (Vue3 + TS + Vant4 + Pinia + ECharts, PWA)           │
│    首页卡片 / 详情抽屉 / 简报 / Scorecard / 数据源状态                     │
└───────────────▲──────────────────────────────────────────────────────────┘
                │ HTTPS: REST(JSON) + SSE(实时)
┌───────────────┴──────────────────────────────────────────────────────────┐
│ L3 接口层  apps/api (FastAPI)                                             │
│    routers/: dashboard, varieties, predictions, news, digest, sources,    │
│              health, admin(手动触发/回放)                                  │
│    职责：鉴权(单用户 token)、参数校验(Pydantic)、只读查询、SSE 广播          │
│    禁止：写业务表、调 LLM、跑采集                                          │
└───────────────▲──────────────────────────────────────────────────────────┘
                │ SQL (SQLAlchemy 2.0 async)
┌───────────────┴──────────────────────────────────────────────────────────┐
│ L2 计算层  jobs/ (Arq Worker，独立进程，按队列消费)                        │
│                                                                          │
│  collector.*   采集 → 原始落库(doc/quote) → 发事件                         │
│  feature.*     生成 FeatureSnapshot(asof)                                │
│  predict.*     08:30 全品种预测 → Prediction                              │
│  revise.*      盘中资讯 → 预期差 → PredictionRevision                      │
│  score.*       15:10 收盘 → Outcome → 命中率/校准                         │
│  explain.*     LLM 生成中文解读（只解释，不定方向）                          │
│  maintain.*    数据质量校验、清理、缓存预热                                 │
└───────────────▲──────────────────────────────────────────────────────────┘
                │ 队列任务 (Redis Streams via Arq)
┌───────────────┴──────────────────────────────────────────────────────────┐
│ L1 数据层                                                                 │
│  PostgreSQL: 关系表 + 快照(jsonb) + 只追加事实表                            │
│    · 行情：quote_1m（分区表，按日分区 + BRIN 索引）                          │
│    · 事实：news_doc / prediction / prediction_revision / outcome           │
│    · 配置：variety / knowledge_node / knowledge_edge / seasonality         │
│    · 治理：model_registry / backtest_run / fetch_log / llm_call_log        │
│  Redis: 任务队列 + 短期缓存（行情最新值、LLM 结果）                          │
│  文件/对象存储：无（个人项目，图表由前端 ECharts 绘制）                       │
└──────────────────────────────────────────────────────────────────────────┘

外部数据源（只经 L2 采集，任何地方不得直连）：
  新浪行情(hq.sinajs.cn) · 新浪期货日线 · 金十快讯 · 东方财富快讯
  · 新浪 7×24 · AKShare(仓单/库存/现货基差，代理多渠道) · FRED(布伦特日线)
```

**为什么不用 Kafka / K8s / 微服务**：个人项目，数据量 ≤ 5 万条/日，Postgres + Redis + 3 个进程已经过剩。企业级 ≠ 组件多，而是**边界清楚、可观测、可回滚**。这套架构在需要规模化时可以无痛替换（Arq→Celery，Postgres→Timescale，Redis→Kafka），因为模块边界是清晰的。

## 4. 技术选型

| 领域 | 选型 | 理由 | 替代方案 |
|---|---|---|---|
| 语言 | Python 3.12 | 生态最全（数据/LLM/采集） | — |
| Web 框架 | FastAPI + Pydantic v2 | 自带 OpenAPI，异步，校验强 | Litestar |
| ORM | SQLAlchemy 2.0 async + Alembic | 迁移可控，async 原生 | Piccolo |
| 数据库 | **PostgreSQL 16**（Supabase Free） | 免费托管、备份、RLS 可选 | Neon（更快的免费 Postgres） |
| 时序存储 | 原生**按日分区表 + BRIN** | 量小（5万/日），无需 Timescale；避免扩展依赖 | TimescaleDB（若 Supabase 支持且需要压缩） |
| 队列/调度 | **Arq**（Redis, asyncio 原生）+ Redis(Upstash) | 比 Celery 轻，原生 async，内置 cron | Dramatiq / Celery |
| 前端 | Vue3 + TS + Vite | 已熟悉，构建快 | React+Next（若需 SSR） |
| UI | **Vant 4**（移动）+ 自定义 CSS 变量 | 国内移动端事实标准，省 60% 样式工作 | NutUI |
| 图表 | ECharts 5（按需引入） | 折线/迷你图/K线齐全 | Chart.js |
| 状态 | Pinia | 官方推荐 | — |
| LLM | DeepSeek（OpenAI 兼容协议） | 成本低、中文强 | 可换任意兼容端点 |
| 观测 | structlog(JSON) + prometheus_client + /live + /ready | 轻量、免费 | Sentry（可选） |
| CI | GitHub Actions | 免费，lint/test/build | — |
| 部署 | Render（api + worker）+ Supabase + Upstash | 全免费、HTTPS、自动部署 | Fly.io / Railway |

## 5. 一天的数据流（时序）

```
T-1 15:00  收盘
   ├─ 15:05  collect.quotes      国内 21 品种日线/分钟落库
   ├─ 15:05  collect.foreign     外盘收盘价（夜盘前值）
   ├─ 15:10  score.outcome       昨日 Prediction vs 今日实际 → outcome
   ├─ 15:15  score.daily         重算滚动命中率/校准曲线
   └─ 16:00  collect.industry    仓单/库存/现货基差（AKShare）

T-1 21:00 ~ T 02:30 外盘交易时段
   └─ 每 60s collect.foreign     外盘实时价 → quote_1m

T 07:30
   └─ feature.build              生成 FeatureSnapshot(asof=T 07:30)
                                 只用 ≤ T-1 收盘 + 隔夜外盘

T 08:30
   ├─ predict.all                21 品种 → Prediction（方向/概率/幅度/置信度）
   ├─ explain.morning            LLM 生成每品种 2 句中文解读（缓存）
   └─ notify                     推送"今日预测已就绪"

T 09:00 ~ 15:00 盘中
   ├─ 每 60s collect.news        资讯入 news_doc
   ├─ news.extract               抽取事件（品种/方向/强度/环节/预期差）
   ├─ revise.check               |预期差| 超阈值 → PredictionRevision + SSE
   └─ 每 60s collect.quotes      行情 + 异动（|涨跌|≥3%）→ SSE

T 15:10
   └─ score.outcome + digest     收盘评分 + 当日简报
```

│  │  │  ├─ models/        # SQLAlchemy 模型（按域分文件）
│  │  │  ├─ routers/
│  │  │  ├─ services/      # 只读查询编排
│  │  │  └─ main.py
│  │  ├─ tests/
│  │  └─ pyproject.toml
│  └─ web/                 # Vue3
│     ├─ src/{api,components,views,stores,styles}
│     └─ vite.config.ts
├─ jobs/                   # Arq worker

### 6.2 代码规范

- `ruff` 格式化 + lint（行宽 100），`mypy` 渐进式（公共模块必须带类型）
- 禁止裸 `except:`；所有外部调用带超时与重试（`tenacity`，指数退避，最多 3 次）
- 所有 DB 写操作必须在事务内；批量写入用 `insert().on_conflict_do_nothing()`
- 时间：DB 统一 **UTC naive**；接口输出 ISO8601 带 Z；前端按 `Asia/Shanghai` 展示
- 日志：结构化 JSON，字段 `ts/level/event/module/trace_id`；不打印密钥与全文正文
- 提交：Conventional Commits；PR 必须过 CI（lint + test + build）

### 6.3 测试策略

| 层 | 手段 | 覆盖目标 |
|---|---|---|
| 单元 | pytest：评分函数、特征计算、去重、校准 | 核心函数 ≥ 80% |
| 集成 | testcontainers 或临时 schema + 真实 Postgres | 采集→入库→预测主链路 |
| 回放 | 固定 fixture（历史 20 交易日快照） | 同一快照必须产出同一预测（确定性） |
| 泄漏 | 断言：预测所用最大时间戳 < 目标日开盘 | 每次 CI 必跑 |
| 契约 | 校验 OpenAPI 与前端类型一致 | 每次 build |

### 6.4 配置与密钥

```
DATABASE_URL=postgresql+asyncpg://...
REDIS_URL=rediss://...
DEEPSEEK_API_KEY=...
DEEPSEEK_BASE_URL=https://api.deepseek.com/v1
DEEPSEEK_MODEL=deepseek-chat
APP_TOKEN=<单用户访问令牌>
TZ=Asia/Shanghai
```
所有变量有默认值或明确标 `required`；启动时校验，缺失直接失败（fail-fast），而不是运行时才发现。

### 6.5 可观测性

| 指标 | 采集方式 | 用途 |
|---|---|---|
| 采集成功率/耗时 | `fetch_log` 表 + Prometheus counter | 数据源健康 |
| 预测产出数 | `prediction` 每日计数 | 08:30 任务是否跑全 |
| LLM 调用次数/成本/缓存命中 | `llm_call_log` | 成本控制 |
| 方向命中率（滚动） | `outcome` 聚合 | 模型是否退化 |
| 接口延迟 P50/P95/P99 | 中间件 | 体验 |

`GET /live` 是存活探针，不触碰 db/redis，进程能响应即 200，供平台健康检查与容器 `HEALTHCHECK` 使用。

`GET /ready` 返回 db/redis/worker 三态：db 或 redis 不可用返回 503（此时 API 不能对外服务）；worker 心跳缺失只把 `status` 置为 `degraded` 并返回 200——worker 是独立进程，它掉线不应触发 API 重启。M1 之后 `/ready` 再叠加"最新行情超过 10 分钟未更新即 degraded"。

## 7. 部署拓扑

```
                 ┌────────────────────────────┐
  手机/电脑 ───▶ │ Render: api (Docker)       │  HTTPS 固定域名
                 │ 静态托管 web/dist + /api    │
                 └───────┬────────────┬───────┘
                         │            │
                 ┌───────▼─────┐  ┌───▼──────────────┐
                 │ Supabase PG │  │ Upstash Redis    │
                 │ (持久化)     │  │ (队列/缓存)       │
                 └───────▲─────┘  └───▲──────────────┘
                         │            │
                 ┌───────┴────────────┴───────┐
                 │ Render: worker (Docker)    │  Arq 常驻
                 └────────────────────────────┘
```

- 免费额度：Render Web Free（15 分钟无访问休眠 → 用外部定时 ping 保活）、Worker 可选 Free 或 Starter；Supabase 500MB；Upstash 10K 命令/日。
- **休眠策略**：08:30 预测任务必须在后台跑完，不依赖用户访问 → worker 独立部署，不被 web 休眠影响。
- 冷启动优化：web 冷启动 ≈ 20s；前端加骨架屏 + 本地缓存上一次 dashboard。

## 8. 安全与合规

- 单用户：`APP_TOKEN` 简单 Bearer 鉴权（PWA 存 localStorage）。不做注册登录。
- 数据源为公开网页/接口，遵守：单源请求间隔 ≥ 60s、设置 UA、失败退避；不批量爬取历史全量以外的内容。
- 不存储任何第三方账号凭据；DeepSeek key 只存环境变量。
- 个人使用，不对外分发数据，不商业化。
